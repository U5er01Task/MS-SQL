## 1. Введение в реляционные базы данных и эволюция MS SQL Server

База данных представляет собой структурированную совокупность данных, организованных по строгим логическим правилам. В корпоративной разработке и веб-архитектуре центральное место занимают системы управления базами данных (СУБД). Они обеспечивают надежное хранение, многопользовательский доступ, транзакционную целостность и защиту информации.

### Реляционная модель данных

Реляционная концепция, предложенная Эдгаром Коддом в 1970 году, опирается на теорию множеств и логику первого порядка. Основные сущности модели:

- **Отношение (Relation):** В физической реализации — двумерная таблица (`Table`), состоящая из строк и колонок.
- **Кортеж (Tuple):** Строка таблицы (`Row` или `Record`), представляющая один экземпляр сущности (например, конкретный заказ или профиль пользователя).
- **Атрибут (Attribute):** Столбец таблицы (`Column` или `Field`), описывающий свойство сущности с фиксированным типом данных.
- **Домен (Domain):** Множество допустимых значений для атрибута (например, диапазон целых чисел от 1 до 100 или валидный формат e-mail).

### Принципы ACID в транзакционных системах

Microsoft SQL Server — это транзакционная СУБД, гарантирующая соблюдение требований ACID:

1. **Atomicity (Атомарность):** Транзакция неделима. Все содержащиеся в ней операции либо завершаются успешно, фиксируя изменения (`COMMIT`), либо полностью отменяются (`ROLLBACK`), возвращая систему в исходное состояние.
2. **Consistency (Согласованность):** Любая транзакция переводит базу данных из одного корректного состояния в другое, не нарушая заданные бизнес-правила, ограничения целостности (`Constraints`) и внешние ключи.
3. **Isolation (Изолированность):** Параллельно выполняемые транзакции не должны влиять друг на друга так, будто они конкурируют за данные без контроля. Уровень изоляции регулирует видимость незафиксированных изменений.
4. **Durability (Долговечность):** Если транзакция зафиксирована, ее результат сохранится даже при аварийном отключении питания или аппаратном сбое сервера.

### История и редакции MS SQL Server

Microsoft SQL Server прошел путь от совместной разработки с Sybase в конце 1980-х до современной высокопроизводительной платформы корпоративного уровня. Современные выпуски поддерживают работу на Windows и Linux, а также облачную инфраструктуру Azure SQL Database.

## 2. Внутренняя архитектура ядра SQL Server Database Engine

Архитектура SQL Server разделена на функциональные уровни, взаимодействующие друг с другом для эффективного выполнения инструкций и распределения ресурсов.

```
+-------------------------------------------------------------+
|                      Client / Application                   |
|            (SSMS, Web Backend via ADO.NET / ODBC)           |
+-------------------------------------------------------------+
                              | TDS Protocol (Port 1433)
+-----------------------------v-------------------------------+
|                        Network Interface                    |
|                Shared Memory / TCP/IP / Named Pipes         |
+-------------------------------------------------------------+
                              |
+-----------------------------v-------------------------------+
|                       Relational Engine                     |
|  - Command Parser (проверка синтаксиса, токенизация)        |
|  - Query Optimizer (оценка стоимости по статистике)         |
|  - Query Execution Engine (исполнение физического плана)    |
+-------------------------------------------------------------+
                              | Access Methods
+-----------------------------v-------------------------------+
|                        Storage Engine                       |
|  - Buffer Pool (кэш страниц данных в оперативной памяти)    |
|  - Transaction Manager (управление блокировками и WAL)      |
|  - Lock Manager (пессимистический контроль конкуренции)     |
+-------------------------------------------------------------+
                              | OS & Disk I/O
+-----------------------------v-------------------------------+
|             Physical Files (.mdf, .ndf, .ldf)               |
+-------------------------------------------------------------+
```

### Relational Engine (Механизм запросов)

1. **Парсер (Command Parser):** Разбирает входящий текст запроса на лексемы, проверяет синтаксис T-SQL и строит синтаксическое дерево.
2. **Альгебраизатор (Algebrizer / Binding):** Связывает имена таблиц, представлений и полей с реальными системными объектами из системного каталога метаданных.
3. **Оптимизатор запросов (Query Optimizer):** Применяет правила трансформации и математическую оценку стоимости (Cost-Based Optimizer). На основе актуальных распределений данных (статистики) формирует физический план выполнения.
4. **План запроса:** Результат работы оптимизатора кэшируется в `Plan Cache`, что устраняет необходимость повторной дорогостоящей компиляции для одинаковых запросов.

### Storage Engine (Механизм хранилища)

Storage Engine управляет выделением страниц памяти, работой с дисковой подсистемой, блокировками и журналированием изменений.

- **Журналирование с упреждением (Write-Ahead Logging / WAL):** Любая модификация строки сначала фиксируется в журнале транзакций на диске, и только после этого страница в оперативной памяти помечается как «грязная» (`Dirty Page`).
- **Контрольная точка (Checkpoint):** Фоновый процесс периодически сбрасывает накопившиеся «грязные» страницы из буферного пула RAM в файлы данных на диске, сокращая время восстановления СУБД при сбоях.
- **Lazy Writer:** Вытесняет старые, редко используемые страницы из буферного пула, если сервер испытывает нехватку оперативной памяти.

## 3. Физическая и логическая организация хранилища

Понимание внутреннего формата хранения страниц позволяет оптимизировать схемы таблиц и правильно выбирать типы данных.

### Файлы базы данных

Каждая база данных в MS SQL Server состоит минимум из двух файлов операционной системы:

- **Primary Data File (`.mdf`):** Основной файл данных. Хранит стартовые системные таблицы, метаданные схемы и пользовательские данные.
- **Secondary Data Files (`.ndf`):** Вспомогательные файлы данных. Используются при масштабировании, разбиении нагрузки по разным физическим дискам и секционировании таблиц.
- **Transaction Log File (`.ldf`):** Файл журнала транзакций. Хранит последовательную цепочку логов всех операций вставки, изменения и удаления для отката и восстановления.

### Страницы (Pages) и экстенты (Extents)

- **Страница данных (Data Page):** Базовая единица ввода-вывода размером ровно **8 КБ (8192 байта)**.
  - 96 байт занимает заголовок страницы (`Header`), содержащий метаданные: тип страницы, идентификатор объекта, указатели на предыдущую и следующую страницы.
  - Полезная нагрузка под строки данных составляет 8060 байт.
  - В конце страницы располагается массив смещений строк (`Row Offset Array`), по 2 байта на строку.
- **Экстент (Extent):** Блок из 8 смежных страниц общим объемом **64 КБ**.
  - _Смешанный экстент (Mixed Extent):_ Содержит страницы разных таблиц или индексов (используется для небольших объектов).
  - _Однородный экстент (Uniform Extent):_ Целиком принадлежит одному объекту.

## 4. Системные базы данных и их роли

Экземпляр SQL Server не может функционировать без четырех встроенных системных баз данных:

1. **`master`:** Мозг экземпляра. Содержит системные конфигурации, сведения об учетных записях (`Logins`), активных конечных точках, расположении всех пользовательских баз и примонтированных файлах. Повреждение `master` блокирует запуск сервера.
2. **`model`:** Шаблон для всех вновь создаваемых баз данных. Любая таблица, пользовательский тип, функция или настройка, добавленная в `model`, автоматически дублируется в каждую новую базу данных при вызове `CREATE DATABASE`.
3. **`msdb`:** База данных планировщика задач (SQL Server Agent). Управляет автоматическими бэкапами, оповещениями операторов, репликацией и пакетами служб интеграции (SSIS).
4. **`tempdb`:** Глобальная временная рабочая область. Служит для хранения временных таблиц (`#temp`, `##temp`), табличных переменных, сортировок при нехватке памяти (`Spill to tempdb`), версий строк при уровне изоляции Snapshot и онлайн-перестроения индексов. При каждом перезапуске SQL Server база `tempdb` пересоздается с нуля.

## 6. Базовые принципы проектирования реляционных схем

Проектирование базы данных начинается с формализации сущностей предметной области и устранения избыточности.

### Нормализация данных (1NF, 2NF, 3NF)

- **Первая нормальная форма (1NF):** Каждая ячейка таблицы содержит атомарное (неделимое) значение, дублирующиеся строки отсутствуют, у таблицы определен первичный ключ. Нельзя хранить список телефонов через запятую в одном текстовом поле.
- **Вторая нормальная форма (2NF):** Таблица находится в 1NF, и каждый неключевой столбец функционально полно зависит от составного первичного ключа целиком, а не от его части.
- **Третья нормальная форма (3NF):** Таблица находится в 2NF, и ни один неключевой атрибут не зависит транзитивно от первичного ключа (зависимость вида `A -> B -> C` устраняется выносом `B` и `C` в отдельную таблицу-справочник).

### Целостность данных и ограничения (Constraints)

- **Primary Key (`PK`):** Уникальный идентификатор строки. Гарантирует уникальность и запрещает значения `NULL`. По умолчанию создает кластеризованный индекс.
- **Foreign Key (`FK`):** Внешний ключ, обеспечивающий ссылочную целостность между таблицами (`REFERENCES ParentTable(Id)`). Защищает от появления «висячих» записей.
- **Unique (`UQ`):** Обеспечивает уникальность значений в столбце, допуская строго одно значение `NULL` (в отличие от некоторых других СУБД).
- **Check (`CK`):** Логическое выражение, валидирующее вставляемые значения (например, `Price > 0`).
- **Default (`DF`):** Подставляет значение по умолчанию при его отсутствии в инструкции `INSERT`.

## 7. Фундаментальные типы данных Transact-SQL

Грамотный подбор типов данных критически важен: он минимизирует размер строки, позволяет уместить больше данных на 8-килобайтной странице, снижает объем ввода-вывода и нагрузку на буферный пул.

### Числовые типы

- `TINYINT`: 1 байт (диапазон 0 .. 255).
- `SMALLINT`: 2 байта (-32 768 .. 32 767).
- `INT`: 4 байта (-2 147 483 648 .. 2 147 483 647).
- `BIGINT`: 8 байт (для огромных счетчиков и транзакционных логов).
- `DECIMAL(p, s)` / `NUMERIC(p, s)`: Фиксированная точность. `p` — общее число знаков, `s` — количество знаков после запятой. Обязателен для финансовых операций (`DECIMAL(18, 4)`).
- `FLOAT` / `REAL`: Числа с плавающей точкой приблизительной точности. Не используются для расчетов цен и валют из-за погрешностей округления.

### Строковые типы

- `CHAR(n)`: Строка фиксированной длины (1 байт на символ для ASCII). Если строка короче `n`, дополняется пробелами справа.
- `VARCHAR(n)`: Строка переменной длины. Хранит ровно столько символов, сколько передано, плюс 2 байта на служебную информацию о длине.
- `NCHAR(n)` / `NVARCHAR(n)`: Юникод-строки (UTF-16, 2 байта на базовый символ). Обязательны для мультиязычных текстов и кириллицы.
- `VARCHAR(MAX)` / `NVARCHAR(MAX)`: Хранилище LOB (Large Object) объемом до 2 ГБ. Данные выносятся за пределы стандартной страницы, если не помещаются в строку.

### Дата и время

- `DATE`: Только дата (ГГГГ-ММ-ДД), занимает 3 байта.
- `TIME`: Только время с настраиваемой точностью долей секунды (3–5 байт).
- `DATETIME2`: Современный стандарт даты и времени с точностью до 100 наносекунд (6–8 байт). Рекомендуется вместо устаревшего `DATETIME`.
- `DATETIMEOFFSET`: Дата и время с учетом смещения часового пояса относительно UTC.

## 8. Практическое руководство по T-SQL: DDL, DML и выборка

Transact-SQL (T-SQL) — проприетарное расширение стандарта ANSI/ISO SQL от Microsoft, включающее процедуры, переменные, циклы и встроенные функции.

### Язык определения данных (DDL)

Создадим базовую схему учебного интернет-магазина:

```sql
-- Создание базы данных с явным указанием первичных параметров файлов
CREATE DATABASE ShopDb
ON PRIMARY
(
    NAME = 'ShopDb_Data',
    FILENAME = 'C:\SQLData\ShopDb_Data.mdf',
    SIZE = 100MB,
    MAXSIZE = 5GB,
    FILEGROWTH = 64MB
)
LOG ON
(
    NAME = 'ShopDb_Log',
    FILENAME = 'C:\SQLData\ShopDb_Log.ldf',
    SIZE = 50MB,
    MAXSIZE = 1GB,
    FILEGROWTH = 32MB
);
GO

USE ShopDb;
GO

-- Таблица клиентов
CREATE TABLE dbo.Customers (
    CustomerId INT IDENTITY(1,1) NOT NULL,
    FirstName NVARCHAR(50) NOT NULL,
    LastName NVARCHAR(50) NOT NULL,
    Email VARCHAR(100) NOT NULL,
    CreatedAt DATETIME2(2) NOT NULL CONSTRAINT DF_Customers_CreatedAt DEFAULT SYSDATETIME(),
    IsActive BIT NOT NULL CONSTRAINT DF_Customers_IsActive DEFAULT 1,
    CONSTRAINT PK_Customers PRIMARY KEY CLUSTERED (CustomerId),
    CONSTRAINT UQ_Customers_Email UNIQUE (Email)
);

-- Таблица заказов со связью через внешний ключ
CREATE TABLE dbo.Orders (
    OrderId INT IDENTITY(1000,1) NOT NULL,
    CustomerId INT NOT NULL,
    OrderDate DATETIME2(0) NOT NULL CONSTRAINT DF_Orders_OrderDate DEFAULT SYSDATETIME(),
    TotalAmount DECIMAL(12, 2) NOT NULL,
    Status VARCHAR(20) NOT NULL,
    CONSTRAINT PK_Orders PRIMARY KEY CLUSTERED (OrderId),
    CONSTRAINT FK_Orders_Customers FOREIGN KEY (CustomerId)
        REFERENCES dbo.Customers (CustomerId)
        ON DELETE NO ACTION
        ON UPDATE CASCADE,
    CONSTRAINT CK_Orders_TotalAmount CHECK (TotalAmount >= 0),
    CONSTRAINT CK_Orders_Status CHECK (Status IN ('Pending', 'Processing', 'Completed', 'Cancelled'))
);
GO
```

### Язык манипулирования данными (DML)

Вставка тестовых записей:

```sql
-- Вставка клиентов
INSERT INTO dbo.Customers (FirstName, LastName, Email)
VALUES
    (N'Иван', N'Петров', 'ivan.petrov@example.com'),
    (N'Анна', N'Смирнова', 'anna.smirnova@example.com'),
    (N'Михаил', N'Кузнецов', 'mikhail.k@example.com');

-- Вставка заказов
INSERT INTO dbo.Orders (CustomerId, TotalAmount, Status)
VALUES
    (1, 15400.50, 'Completed'),
    (1, 2300.00, 'Processing'),
    (2, 45990.00, 'Completed'),
    (3, 1200.00, 'Pending');
```

Модификация и удаление записей:

```sql
-- Обновление статуса заказа
UPDATE dbo.Orders
SET Status = 'Processing'
WHERE OrderId = 1003 AND Status = 'Pending';

-- Удаление неактивных клиентов без заказов
DELETE FROM dbo.Customers
WHERE IsActive = 0
  AND CustomerId NOT IN (SELECT DISTINCT CustomerId FROM dbo.Orders);
```

### Аналитические выборки и агрегация

Объединение таблиц (`JOIN`), группировка и фильтрация:

```sql
-- Получение статистики по клиентам, суммам заказов и количеству покупок
SELECT
    c.CustomerId,
    CONCAT(c.LastName, ' ', c.FirstName) AS FullName,
    c.Email,
    COUNT(o.OrderId) AS OrdersCount,
    COALESCE(SUM(o.TotalAmount), 0.00) AS TotalSpent,
    AVG(o.TotalAmount) AS AverageCheck
FROM dbo.Customers AS c
LEFT JOIN dbo.Orders AS o
    ON c.CustomerId = o.CustomerId
    AND o.Status = 'Completed'
WHERE c.IsActive = 1
GROUP BY
    c.CustomerId,
    c.LastName,
    c.FirstName,
    c.Email
HAVING COUNT(o.OrderId) > 0
ORDER BY TotalSpent DESC;
```

## 9. Введение в индексацию: Clustered vs Nonclustered Indexes

Индексы в реляционных базах данных аналогичны предметному указателю в конце книги. Без индекса SQL Server вынужден производить полное сканирование таблицы (`Table Scan`), считывая абсолютно каждую страницу с диска в память.

```
       B-Tree (Сбалансированное дерево индекса)
                      [ Root Page ]
                     /             \
         [ Intermediate ]        [ Intermediate ]
          /            \          /            \
    [ Leaf Page ] [ Leaf Page ] [ Leaf Page ] [ Leaf Page ]
```

### Кластеризованный индекс (Clustered Index)

- Определяет физический порядок хранения строк в таблице.
- Таблица может иметь **только один** кластеризованный индекс (нельзя отсортировать физические страницы одновременно по двум разным критериям).
- Листовой уровень (`Leaf Level`) кластеризованного индекса — это и есть сами реальные страницы данных со всеми колонками таблицы.
- Таблица без кластеризованного индекса называется **кучей (Heap)**.

### Некластеризованный индекс (Nonclustered Index)

- Хранится отдельно от физических данных таблицы в собственном B-дереве.
- Листовой уровень не содержит всех данных строки, а хранит только индексный ключ и указатель на местоположение строки:
  - Если у таблицы есть кластеризованный индекс, указатель — это значение кластеризованного ключа.
  - Если таблица является кучей, указатель — физический идентификатор строки `RID` (File:Page:Slot).
- Начиная с SQL Server 2005 поддерживаются покрывающие индексы с предложением `INCLUDE`:
  ```sql
  -- Индекс для ускорения поиска заказов клиента с исключением Lookup-операций
  CREATE NONCLUSTERED INDEX IX_Orders_CustomerId_Status
  ON dbo.Orders (CustomerId, Status)
  INCLUDE (TotalAmount, OrderDate);
  ```

## 10. Безопасность, резервное копирование и регламентные операции

Надежность хранения данных напрямую зависит от выстроенного контура безопасности и стратегии резервного копирования.

### Модель безопасности

- **Logins (Имена входа):** Создаются на уровне сервера (экземпляра SQL Server). Аутентификация бывает Windows Authentication (предпочтительна по соображениям безопасности Kerberos) и SQL Server Authentication (логин и пароль хранятся в master).
- **Users (Пользователи базы данных):** Объект конкретной базы данных, сопоставленный с серверным логином.
- **Roles (Роли):** Группы привилегий (например, `db_datareader`, `db_datawriter`, `db_owner`) для реализации ролевой модели доступа (`RBAC`).

### Стратегии резервного копирования

1. **Full Backup (Полный бэкап):** Копирует все страницы данных и часть журнала для обеспечения согласованности на момент окончания резервного копирования.
2. **Differential Backup (Разностный бэкап):** Копирует только те экстенты данных, которые изменились с момента последнего полного бэкапа.
3. **Transaction Log Backup (Бэкап лога):** Копирует журнал транзакций и производит его усечение (`Truncation`). Позволяет восстановить базу данных на произвольную миллисекунду времени (`Point-in-Time Recovery`).

```sql
-- Пример ручного создания полного бэкапа базы данных
BACKUP DATABASE ShopDb
TO DISK = 'C:\SQLBackups\ShopDb_Full.bak'
WITH FORMAT,
     MEDIANAME = 'ShopDbBackups',
     NAME = 'Full Backup of ShopDb',
     COMPRESSION,
     STATS = 10;
GO
```
